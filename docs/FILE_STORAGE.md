# Local versioned files

File names, directories, ownership and the current version come from PostgreSQL
`files` and `file_versions`. Content is stored beneath `STUDY_ROOT` as
`objects/<user_id>/<file_id>/<version_id>/content`. Logical paths never determine
object locations. The local bind mount remains required.

`app/services/file_records.py` authorizes every file/version lookup using the
authenticated user. REST, MCP and indexing use this service. `app/storage/base.py`
defines content operations; `local.py` implements immutable local objects and
translates storage failures. No S3 client or cloud credentials are needed for B2.

## Import and cutover

Existing installations must import before starting the new file browser. Do this
in a maintenance window using the new image/code with application writers stopped:

1. Take the existing database and material-directory backup. Stop web/API file
   writes, internal indexing and external n8n or cron writers.
2. Apply the B1 additive migration with the normal maintenance entry point.
3. With runtime `DATABASE_URL` and the existing writable `STUDY_ROOT` mounted,
   run the following once for each owning user:

   ```sh
   uv run --no-sync python scripts/import_local_files.py --user-id USER_UUID
   ```

   The default source is `STUDY_ROOT/USER_UUID`. `--source-root` may name another
   legacy directory belonging to that user. UUID names and object keys are
   generated by the server. Import does not rename or delete source files.
4. Read the JSON report and require `errors` to be empty. It reports file and
   directory counts, total bytes, copied/reused files, and linked old indexes.
   Rerunning verifies and reuses matching records and objects, including a
   pending first version left by an interrupted import. Content conflicts,
   stale old indexes and missing indexed source files cause a nonzero exit.
   For a stale old index, rebuild from the imported records with
   `scripts/index_files.py`, then rerun import and verify its report.
5. Start the new application only after all users pass verification. Resume only
   writers that use the new upload service. A workflow that writes directly to
   the legacy directory must remain stopped until it uses versioned uploads.
   `/api/files/sync-materials` returns 503 until the versioned workflow is connected
   in B8, preventing an old webhook from reporting invisible new files.

Retain source trees and the pre-cutover backup through the rollback window.
There is no dual-write mode. After new uploads begin, rolling back application
code alone cannot expose those new objects to the old path-based browser;
coordinate any data rollback with the backup point. Do not automatically delete
legacy trees or completed version objects. Object retention/cleanup and cloud
migration are B8 work.

The import is separate from SQL migrations so deployments cannot enforce
non-null index references before data verification. The subsequent B1 constraint
tightening migration must be delivered after every user's backfill has passed;
it is not automatically bundled with B2.

## Current behavior

`POST /api/files/upload-url` accepts a logical `path` and returns `file_id`,
`version_id`, `url` and `headers`. PUT the bytes to that URL under the same user
session. Local PUT verifies ownership, saves immutable bytes, completes the
version and advances the current revision in one database transaction. A late
older upload cannot replace a newer completed revision. Reusing a completed PUT
target returns 409. Retrying an interrupted pending PUT accepts only identical
already-published bytes.

Download URLs pin a file/version pair and still require session authentication;
they are not standalone bearer grants. Path-based `/api/files/raw?path=...`
resolves the current version and requires cache revalidation. Version URLs have
separate browser cache entries. PDFs/images keep inline presentation, safe
download headers and byte-range support. A soft-deleted file cannot be downloaded
through an old version URL.

Empty directories are database records, with no `.keep` object. File and directory
renames update metadata in a transaction without moving version objects. Deletes
hide the affected subtree; bytes remain available for the future retention policy.

`scripts/index_files.py` and the existing internal reindex endpoints enumerate
completed database versions rather than scanning the legacy disk tree. They
retain the existing text extraction and PostgreSQL search. Search resolves current
names and excludes deleted files and indexes for an older current version. Web
uploads do not yet automatically start indexing; reliable per-file tasks and
their UI are connected in B3–B6.

Backups still archive the local root. Restore verification checks every completed
local version's object reference, including historical and not-yet-indexed files.
